¿Cómo resolver la edición de períodos temporales?

El problema central: la fecha de inicio es la clave del período y hoy no se puede corregir

A

Corregir inicio en el editor

El modal de edición añade la fecha de inicio como campo editable. El backend recibe una operación "correct-start-date" que mueve el período sin romper la continuidad.

A favor

  • Flujo mínimo — mismo modal, un campo más
  • Intuitivo: editas lo que está mal
  • Pequeño scope frontend + backend

En contra

  • Requiere nuevo endpoint backend
  • Validación compleja (no puede solapar con período anterior)
B

Eliminar período + volver a crear

Se añade acción "Eliminar" a los períodos no vigentes, y "Reemplazar desde fecha" clarifica que cierra el actual y abre uno nuevo. Para el caso de un único período activo: se elimina y se recrea con la fecha correcta.

A favor

  • Operaciones simples y explícitas
  • Delete ya existe conceptualmente en el backend

En contra

  • Flujo en dos pasos — poco ergonómico
  • No funciona si el período tiene restricciones de integridad (presencia activa)
  • Necesita UI para gestionar el estado intermedio
C

Período completamente editable (full-edit)

Cada fila del período table es completamente editable: fecha inicio, fecha fin y contenido en un solo formulario. El backend expone un PATCH completo que recalcula la continuidad.

A favor

  • UX más directa — editas exactamente lo que ves
  • Elimina la distinción create / correct / close — todo es editar
  • Modelo mental más limpio

En contra

  • Mayor scope backend (PATCH completo con validaciones complejas)
  • Riesgo de romperse la historia temporal si el usuario edita fechas sin entender el impacto
  • Más difícil de auditar

Contexto adicional

El enfoque actual ya tiene replace (cierra el actual y crea uno nuevo desde fecha), correct (edita el contenido sin tocar fechas) y close (pone fecha fin). Lo que falta es poder mover la fecha de inicio de un período existente.
